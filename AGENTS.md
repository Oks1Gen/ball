# Правила проекта

- Агенту запрещено выполнять работу над проектом без работающего сервера Rojo. Перед началом работы проверить, что запущен `rojo serve default.project.json --port 34872` из папки `RojoTest` и сервер отвечает по адресу `http://localhost:34872`. Если сервер не запущен, запустить его в фоне со скрытым окном, проверить доступность и только затем продолжать работу. Не запускать дубликат уже работающего сервера. Если запуск или проверка не удались, остановить работу над проектом и сообщить пользователю причину. Проверка и запуск Rojo разрешены для выполнения этого правила.
- Мобильный UI не тестировать в обычных задачах. Проверки телефона отложены до финальной подготовки к релизу; раньше проводить их только по отдельной прямой просьбе пользователя. Когда такая проверка нужна, использовать только ландшафт (например, iPhone 17 Pro → LandscapeRight): игра рассчитана на горизонтальный экран. Портрет не воспроизводить. После проверки возвращать симулятор к обычному виду.
- Не использовать Computer Use для работы с этим проектом: ни навык, ни инструменты автоматизации интерфейса, включая `@oai/sky` и `cua_repl`.
- Для работы с Roblox Studio использовать Studio MCP. Если подключение недоступно, сообщить об этом пользователю; не обходить ограничение автоматизацией мыши, клавиатуры или интерфейса через другие средства.

## Стек и документация

- Корень Git содержит `rokit.toml`; исходники и Wally-проект находятся в `RojoTest/`.
- Стек: Luau, Rokit, Rojo, Wally, React Luau/ReactRoblox, Ripple, серверный ProfileStore. Knit не добавлять.
- Порядок чтения: `docs/README.md`, затем документы по задаче. Историческое описание сцены и механик находится в `RojoTest/README.md`.
- Проверки: `node RojoTest/tools/check.mjs`. Запуск и остановка Rojo: `StartRojo.bat` и `StopRojo.bat`.
- Исходники менять на диске и синхронизировать через Rojo. Ручную сцену не пересоздавать при обновлении кода.
- Не коммитить и не публиковать игру без явной просьбы пользователя.

## Компоновка мира

- Обязательный контракт сцены — `docs/world-structure.md`: мир → зона → законченный объект. В корне каждого мира только `Lobby`, `FootballCourse`, `TrainingArea`.
- Folder использовать для категорий, Model — для целого переносимого объекта. Стенд, его мячи, пьедесталы, BillboardGui и точки покупки обязаны принадлежать одному `BallShop`; каждый слот — отдельная Model.
- Декор хранить в своей зоне; свободные цветы — в её `Environment/Flowers`, детали клумбы/дерева/стенда — внутри этого объекта. Не создавать общие свалки деталей или папки `Improved`, `Polish`, `Fix`, `New` в готовой карте.
- У невидимых частей указывать `PartRole` и понятное назначение; сохранять нужные коллизии, триггеры и точки взаимодействия. Не удалять детали по одной прозрачности. Заменённые неактивные оригиналы и исходные ассеты хранить вне Workspace.
- Подтверждённый прозрачный мусор удалять, а не складировать: только после проверки физики, визуальных дочерних объектов, ссылок и использования в коде. `TransparentCleanup` запускается после финальной компоновки; критерии и проверки — `docs/transparent-cleanup.md`. Рабочие исходники, цели, опоры и журнал миграции мусором не считать.
- Игровой код получает объекты через `Shared.WorldRefs`. Исторические пути допустимы только в старых строительных модулях и миграциях. В игре остался только World1; World2 не создавать. Финальная компоновка `WorldLayout.apply` обязательна после сборки World1; новые модули создают объекты сразу по контракту.
- Изменение структуры должно сохранять CFrame/Size/видимость/физику, ссылки и поведение игры. Проверять `tools/VerifyWorldLayout.luau`, обратимость, повторную сборку и Play. Процедура работы со старыми строительными модулями описана в `docs/world-structure.md`.

## Update Log

- Вести игровой журнал в `RojoTest/src/client/Modules/UpdateLog.luau`: это единственный источник записей для окна Update Log.
- При каждом завершённом изменении, заметном игроку (функция, интерфейс, баланс, исправление), в той же задаче добавлять краткую запись на английском: что изменилось для игрока. Внутренние рефакторинги и инструменты без изменения поведения в журнал не добавлять.
- Новые записи размещать сверху: уникальный `id` с датой `YYYY-MM-DD` (при нескольких выпусках за день — суффикс), отображаемая дата, заголовок и список `changes`. Дополнения текущей задачи объединять в одну запись; старую историю сохранять. Не выдавать планы и непроверенные изменения за выпущенные.
- Проверять открытие/закрытие журнала, прокрутку и читаемость на ПК. Мобильную проверку журнала, как и остального UI, отложить до подготовки релиза или отдельной просьбы пользователя. Иконку, промпт и Roblox Image ID хранить в `Assets/UI/` по принятому формату.
