# Правила проекта

- Агенту запрещено выполнять работу над проектом без работающего сервера Rojo. Перед началом работы проверить, что запущен `rojo serve default.project.json --port 34872` из папки `RojoTest` и сервер отвечает по адресу `http://localhost:34872`. Если сервер не запущен, запустить его в фоне со скрытым окном, проверить доступность и только затем продолжать работу. Не запускать дубликат уже работающего сервера. Если запуск или проверка не удались, остановить работу над проектом и сообщить пользователю причину. Проверка и запуск Rojo разрешены для выполнения этого правила.
- Мобильный UI не тестировать в обычных задачах. Проверки телефона отложены до финальной подготовки к релизу; раньше проводить их только по отдельной прямой просьбе пользователя. Когда такая проверка нужна, использовать только ландшафт (например, iPhone 17 Pro → LandscapeRight): игра рассчитана на горизонтальный экран. Портрет не воспроизводить. После проверки возвращать симулятор к обычному виду.
- Не использовать Computer Use для работы с этим проектом: ни навык, ни инструменты автоматизации интерфейса, включая `@oai/sky` и `cua_repl`.
- Для работы с Roblox Studio использовать Studio MCP. Если подключение недоступно, сообщить об этом пользователю; не обходить ограничение автоматизацией мыши, клавиатуры или интерфейса через другие средства.

## Стек и документация

- Корень Git содержит `rokit.toml`; исходники и Wally-проект находятся в `RojoTest/`.
- Стек: Luau, Rokit, Rojo, Wally, React Luau/ReactRoblox, Ripple, серверный ProfileStore. Knit не добавлять.
- Порядок чтения: `docs/README.md`, затем документы по задаче. Историческое описание сцены и механик находится в `RojoTest/README.md`.
- Проверки: `node RojoTest/tools/check.mjs`. Запуск и остановка Rojo: `StartRojo.bat` и `StopRojo.bat`.
- Исходники менять на диске и синхронизировать через Rojo. Ручную сцену не пересоздавать при обновлении кода.
- При уборке файлов и ассетов сохранять текущую новую карту: не запускать строительные модули или `WorldLayout.prepare` ради проверки такой уборки. Предпочитать читающие проверки и Play. В Edit учитывать кэш `require`: для необходимого отдельно разрешённого перестроения загружать свежие модули вместе с их зависимостями, иначе старый кэш может заменить новый декор.
- Не коммитить и не публиковать игру без явной просьбы пользователя. Явная просьба сделать push разрешает необходимые коммит и отправку текущих изменений в настроенный upstream (для этого проекта `origin/main`, `Oks1Gen/ball`) без повторного подтверждения, в том числе если репозиторий публичный. Перед очисткой сначала успешно отправить резервный снимок. Это не разрешает force-push, смену remote или публикацию игры. Обязательные ограничения среды всё равно соблюдать; при блокировке объяснить её конкретную причину.

## Компоновка мира

- Строительные блоки со studs получают материал по [docs/hd-studs.md](docs/hd-studs.md). Описание старых накладок в документах карты относится к существующей сцене.

- Обязательный контракт сцены — `docs/world-structure.md`: мир → зона → законченный объект. В корне каждого мира только `Lobby`, `FootballCourse`, `TrainingArea`.
- Folder использовать для категорий, Model — для целого переносимого объекта. Стенд, его мячи, пьедесталы, BillboardGui и точки покупки обязаны принадлежать одному `BallShop`; каждый слот — отдельная Model.
- Декор хранить в своей зоне; свободные цветы — в её `Environment/Flowers`, детали клумбы/дерева/стенда — внутри этого объекта. Не создавать общие свалки деталей или папки `Improved`, `Polish`, `Fix`, `New` в готовой карте.
- Для наземного декора проверять полное пятно контакта с видимой опорой, включая углы и кромки. Если основание пересекает край, щель или перепад высот, переставить объект, изменить его размер или спроектировать опору. Перед сдачей проверить сбоку с уровня игрока. Подробности — `docs/world-structure.md`.
- У невидимых частей указывать `PartRole` и понятное назначение; сохранять нужные коллизии, триггеры и точки взаимодействия. Не удалять детали по одной прозрачности. Заменённые неактивные оригиналы и исходные ассеты хранить вне Workspace.
- Подтверждённый прозрачный мусор удалять, а не складировать: только после проверки физики, визуальных дочерних объектов, ссылок и использования в коде. `TransparentCleanup` запускается после финальной компоновки; критерии и проверки — `docs/transparent-cleanup.md`. Рабочие исходники, цели, опоры и журнал миграции мусором не считать.
- Игровой код получает объекты через `Shared.WorldRefs`. Исторические пути допустимы только в старых строительных модулях и миграциях. World2 можно создавать по контракту сцены. Финальная компоновка `WorldLayout.apply` обязательна после сборки World1; новые модули создают объекты сразу по контракту.
- Изменение структуры должно сохранять CFrame/Size/видимость/физику, ссылки и поведение игры. Проверять `tools/VerifyWorldLayout.luau`, обратимость, повторную сборку и Play. Процедура работы со старыми строительными модулями описана в `docs/world-structure.md`.

## Update Log

- Единственный источник версий, записей и авторов — `RojoTest/src/client/Modules/UpdateLog.luau`; обязательный формат и процедура — `docs/update-log.md`. Отображение — `Controllers/UpdateLogView.luau` в общей оболочке `HudPanels`.
- При каждом завершённом изменении, заметном игроку, в той же задаче обновлять журнал на английском. Мелкие правки за одну дату Europe/Moscow объединять в текущий неопубликованный выпуск, похожие пункты переписывать по итоговому результату без повторов и промежуточных вариантов. Внутренние изменения, планы и непроверенные результаты не включать.
- Поддерживать версию `major.minor.patch`: patch — небольшие улучшения/исправления, minor — новая механика/крупная переработка (patch сбрасывается), major — согласованный крупный релиз (minor/patch сбрасываются). Число задач и пунктов версию не повышает. База новой истории — `0.1.0`; новую версию создавать при новой дате или после публикации текущей, до публикации мелкие дополнения номер не меняют. Крупное изменение текущего черновика может повысить его minor, сохраняя один выпуск.
- У выпуска обязательны уникальные `id = YYYY-MM-DD-vX.Y.Z`, `date`, `version`, `title`, `published`, `changes`. Каждый пункт: стабильный `id`, категория `New`/`Improved`/`Fixed`, короткий `summary`, необязательные подробности и непустые `credits` (автор + вклад). Цель — 3–5 содержательных пунктов, максимум 5; одиночный фикс допустим. Микроизменения объединять, технические детали в игроковый текст не переносить.
- В Update Log указывать только конкретных игроков с подтверждёнными никами и явно описывать, какой игрок что сделал в каждом пункте. Запрещены коллективные и безличные подписи: `Ball Team`, `Team`, «команда», «разработчики» и аналоги. Не упоминать ИИ, AI, Codex, ботов или инструменты как авторов либо исполнителей — ни в credits, ни в заголовках, ни в подробностях. Если игрок или его вклад неизвестен, уточнить у пользователя до добавления записи; не придумывать авторство и не подставлять команду.
- Для авторства брать ник игрока из Studio Play через Studio MCP (`Players.LocalPlayer.Name` в клиенте). Если пользователь явно назвал автора, использовать указанный ник. Если Studio Play недоступен или ник определить не удалось, уточнить его у пользователя. Для подтверждённого аккаунта показывать аватар, для игрока без подтверждённого UserId — его подтверждённый ник текстом. Вклад указывать в подробностях каждого пункта.
- UI объединяет выпуски под одной карточкой даты, новые даты/версии сверху; показывает четыре последние даты. Историю после начальной очистки не удалять из данных ради лимита UI. Опубликованный выпуск (`published=true`) не дополнять новыми изменениями; создавать следующий номер в той же карточке даты. Флаг публикации менять только после фактической явно разрешённой публикации игры; обновление журнала не разрешает публикацию.
- Проверять на ПК открытие/закрытие, раскрытие/сворачивание, авторов, прокрутку и читаемость; при изменении модели — Lune-тесты журнала и `node RojoTest/tools/check.mjs`. Мобильную проверку отложить до подготовки релиза или отдельной просьбы. Иконку, промпт и Roblox Image ID хранить в `Assets/UI/` по принятому формату.
